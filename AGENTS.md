# AGENTS.md - Designer Atelier Landing

## Project Identity
- This repo is an Astro static landing page for an independent graphic designer / visual design atelier.
- Primary goal: make a visitor trust the designer quickly and feel ready to send a brief.
- Site language is English. Copy should sound natural, confident, commercial, and editorial; do not over-explain that the designer works in English.
- Visual direction: premium editorial, tactile print culture, hospitality/campaign design, refined motion, strong conversion clarity.

## Non-Negotiable Design Bar
- Do not ship generic SaaS-style UI, default purple gradients, bland card grids, or stock-looking layouts.
- Every major section should have a visual reason to exist: composition, image, motion, typographic contrast, proof, or conversion value.
- First viewport must create immediate desire: strong headline, clear offer, credible work preview, and obvious brief CTA.
- Prioritize readable hierarchy over decorative density. If a layout looks visually rich but hard to scan, simplify it.
- Preserve the atelier/editorial personality: warm off-white paper, deep ink, brass/gold accents, serif display type, mono labels, print-inspired textures.

## Content And Copy Rules
- Keep all user-facing website copy in English unless the user explicitly asks otherwise.
- Write for clients buying design outcomes, not designers admiring process jargon.
- Avoid awkward phrases, forced mentions of language, AI-sounding claims, or overpromising metrics.
- Preferred tone: specific, direct, premium, useful.
- CTA wording should stay practical: `Send a Brief`, `View the Work`, `Start a Project`, or similarly natural phrases.
- When adding a new claim, make sure the page visually supports it with work examples, process clarity, or service details.

## Source Structure
- `src/pages/index.astro` is the page composition entrypoint.
- `src/components/*.astro` own section markup and should stay focused by section.
- `src/data/site.ts` owns global site identity, metadata, nav, and hero-level copy.
- `src/data/works.ts` owns portfolio/work data.
- `src/data/services.ts` owns service/package content.
- `src/data/conversion.ts` owns conversion, proof, process, and booking content.
- `src/scripts/landing.ts` owns browser-side interactions and progressive enhancement.
- `src/styles/global.css` imports CSS partials.
- `src/styles/partials/*.css` own the visual system by area; avoid dumping unrelated styles into one file.

## Image And Asset Workflow
- Original source images belong in `public/assets/original/`.
- Optimized responsive images belong in `public/assets/works/` and should generally be generated by `pnpm optimize:images`.
- Portfolio image data must match generated asset filenames in `src/data/works.ts`.
- Prefer AVIF/WebP responsive assets for rendered work imagery; avoid pointing production components at large original PNG/JPG files unless there is a deliberate reason.
- Do not crop key poster/menu artwork in a way that hides important typography or product context. Use `object-fit: contain` or dedicated composition wrappers when the full artifact matters.
- Keep decorative generated assets lightweight and purposeful; avoid adding huge images for minor background effects.

## Layout And Responsiveness
- Check desktop, tablet, and mobile layouts after any visual change.
- Watch for common regressions: horizontal overflow, overlapping cards, clipped artwork, illegible labels, CTA buried below visual noise, and text lines that are too long.
- Hero, showcase, work gallery, services, process, and contact sections must each remain readable independently.
- Responsive CSS should be consolidated and intentional. Do not add scattered one-off breakpoints unless a component genuinely needs them.
- Prefer fluid sizing with `clamp()`, CSS variables, grid/flex composition, and section-level constraints.

## Motion And Interaction
- Motion should feel polished, not noisy. Use it to guide attention or add tactility.
- Keep interactions progressive: the page must remain usable if JavaScript is slow or unavailable.
- Respect `prefers-reduced-motion`; do not add required motion for core comprehension.
- For 3D tilt, carousel, counters, reveal, or progress effects, ensure they do not block scrolling, accessibility, or mobile usability.
- Keep interaction code in `src/scripts/landing.ts` modular enough to debug; avoid anonymous large blocks with hidden shared state.

## Accessibility And SEO
- Maintain semantic sections, useful headings, descriptive alt text, and keyboard-accessible controls.
- Interactive controls must have clear labels and should work without relying on hover only.
- `src/components/BaseHead.astro` and `src/data/site.ts` are the source for metadata decisions.
- Do not degrade title, description, canonical/social metadata, or image dimensions when changing SEO.

## Engineering Rules
- This is a static Astro project. Avoid adding heavy frontend frameworks or runtime dependencies unless the benefit is clear and approved.
- Keep data-driven content in `src/data/*`; do not hardcode repeated portfolio/service content directly inside section components.
- Prefer small, readable Astro components over monolithic markup.
- Use CSS variables already present in the design system before introducing new raw colors or spacing scales.
- Do not commit generated `dist/`, `.astro/`, `.DS_Store`, or local browser/test artifacts.
- Preserve existing user work. Check `git status --short --branch` before edits and before commit/push.

## Verification
- Minimum check after code/style/content changes: `pnpm build`.
- After image source or asset changes: run `pnpm optimize:images`, then `pnpm build`.
- After meaningful UI/layout changes: verify in a browser at desktop and mobile widths; check console errors and horizontal overflow.
- If using the local dev server, prefer `pnpm dev -- --host 127.0.0.1` and open `http://127.0.0.1:4321/`.
- Report exactly what was run and what remains unverified.

## Git And Delivery
- Use concise commit messages that describe user-visible or engineering value.
- Prefer fast-forward pulls: `git pull --ff-only`.
- Do not force push unless the user explicitly approves and the risk is explained.
- Before pushing, confirm the branch, remote, latest commit, and clean working tree.
- From now on, after each completed change loop, commit and push the finalized work to the configured remote unless the user explicitly says not to.
